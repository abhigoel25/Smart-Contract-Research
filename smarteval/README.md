# SmartEval: LLM-Generated Solidity Smart Contract Benchmark

## Overview

This dataset supports empirical research on the quality of Solidity smart contracts generated by large language models (LLMs) from natural language specifications. It combines two components: the FSM-SCG source dataset, which provides natural language specifications, formal finite state machine (FSM) descriptions, and expert-written ground-truth Solidity implementations, and the SmartEval generated contracts corpus, which provides 9,000 LLM-generated contracts produced from a subset of FSM-SCG specifications along with five-dimensional quality evaluations, security audit reports, ABI artifacts, and compilation results for each.

The intended evaluative use is benchmarking LLM code generation quality for smart contracts, studying failure modes in specification-to-code synthesis, and comparing LLM-generated implementations against expert developer baselines across structured quality dimensions.

---

## Dataset Components

### Component 1: FSM-SCG Source Dataset

**File:** `requirement_fsm_code.jsonl`
**Format:** JSONL (one JSON object per line)
**Entries:** 21,976
**Size:** ~192 MB

This is the source dataset from which the 9,000 SmartEval contracts were generated. Each line is a self-contained JSON object with the following fields:

| Field | Type | Description |
|---|---|---|
| `user_requirement` | string | Natural language description of the contract specification, avg. 120 words |
| `FSM` | string | Formal finite state machine specification including states, transitions, guard conditions, and triggered actions |
| `version` | string | Solidity version of the ground-truth implementation (range: 0.4.x to 0.8.x) |
| `code` | string | Expert-written ground-truth Solidity implementation, avg. 85 lines |

Contract categories covered include ERC20 and ERC721 token standards (~42%) and custom business logic contracts including crowdsales, governance systems, staking, escrow, and access control (~58%).

### Component 2: SmartEval Generated Contracts Corpus

**Files:** `smarteval_contracts.jsonl` and `contracts/`
**Format:** JSONL (one JSON object per line) plus per-contract Solidity and evaluation files
**Entries:** 9,000
**Generation model:** GPT-4o-mini
**Compiler:** solc (`0.8.33+commit.64118f21`), with pragma normalization applied to support contracts across Solidity versions 0.4.x through 0.8.x

#### Directory Structure

```
smarteval/
├── README.md
├── requirement_fsm_code.jsonl        # FSM-SCG source dataset (21,976 entries)
├── smarteval_contracts.jsonl         # All 9,000 generated contracts (consolidated)
└── contracts/
    ├── 0001/
    │   ├── contract.sol              # Generated Solidity source code
    │   └── quality_evaluation.json  # Five-dimensional quality evaluation
    ├── 0002/
    │   ├── contract.sol
    │   └── quality_evaluation.json
    └── ...                           # Through 9000/
```

`smarteval_contracts.jsonl` is the primary data file and contains every field needed for analysis, including the Solidity code, ABI, security audit, evaluation scores, and ground-truth comparison for all 9,000 contracts. The `contracts/` directory provides the same Solidity source and quality evaluation in standalone files for users who prefer to browse individual contracts without loading the full JSONL.

Each entry corresponds to one FSM-SCG specification and contains the following fields:

| Field | Type | Description |
|---|---|---|
| `contract_id` | integer | Sequential identifier for the generated contract |
| `batch_id` | string | Batch run identifier (format: `YYYYMMDD_HHMMSS`) |
| `timestamp` | string | ISO 8601 timestamp of generation |
| `contract_text` | string | The natural language specification used as input (truncated in some entries; full text in the matched FSM-SCG entry) |
| `latency_seconds` | float | Total wall-clock time for the full pipeline to process this contract |
| `phase_times` | object | Per-phase timing breakdown (phase_1 through phase_7) in seconds |
| `solidity_code` | string | The LLM-generated Solidity contract |
| `ground_truth_code` | string | The expert-written ground-truth Solidity contract from FSM-SCG |
| `abi` | array | JSON ABI array for the generated contract |
| `audit_report` | object | Security audit report (may be empty object `{}` for some entries) |
| `generated_evaluation` | object | Five-dimensional quality evaluation of the generated contract (see Evaluation Schema below) |
| `ground_truth_evaluation` | object | Five-dimensional quality evaluation of the ground-truth contract using the same rubric |
| `quality_evaluation` | object | Duplicate of `generated_evaluation`; included for compatibility |
| `generated_score` | float | Deterministically recomputed composite score for the generated contract (0 to 100) |
| `generated_grade` | string | Letter grade for the generated contract (A, B, C, D, or F) |
| `generated_compiles` | boolean | Whether the generated contract compiled successfully under solc 0.8.x |
| `ground_truth_score` | float | Deterministically recomputed composite score for the ground-truth contract |
| `ground_truth_compiles` | boolean | Whether the ground-truth contract compiled successfully |
| `score_delta` | float | Difference between generated score and ground-truth score (generated minus ground truth) |
| `final_score` | float | Same as `generated_score` |
| `grade` | string | Same as `generated_grade` |
| `compiles` | boolean | Same as `generated_compiles` |
| `compilation_error` | string or null | Compiler error message if compilation failed, otherwise null |
| `metric_scores` | object | Raw per-metric integer scores (keys: `functional_completeness`, `variable_fidelity`, `state_machine`, `business_logic`, `code_quality`) |

#### Evaluation Schema

Both `generated_evaluation` and `ground_truth_evaluation` share the same structure. The composite score is computed as:

```
Score = 0.25 * M1 + 0.15 * M2 + 0.15 * M3 + 0.35 * M4 + 0.10 * M5
```

| Field | Metric | Weight | Description |
|---|---|---|---|
| `metric_1_functional_completeness` | M1 | 25% | Function name matching (exact and semantic) plus implementation quality including access control, events, and input validation |
| `metric_2_variable_fidelity` | M2 | 15% | State variable naming consistency, correct Solidity types, and active use in logic |
| `metric_3_state_machine` | M3 | 15% | FSM state definition, transition implementation, and guard enforcement |
| `metric_4_business_logic` | M4 | 35% | Obligation implementation, financial logic accuracy, temporal constraints, and conditional flows |
| `metric_5_code_quality` | M5 | 10% | Absence of placeholders, NatSpec documentation, event quality, and code structure |

Each metric object contains `score` (integer, 0 to 100), detailed sub-field breakdowns, line-level `evidence`, and a `points` tally. The `composite_score` sub-object within each evaluation records the weighted contribution of each metric and a `final_score`. All composite scores in the top-level fields are deterministically recomputed from raw metric values in post-processing rather than accepted from LLM-generated aggregates.

#### Per-Contract Artifact Files

Each of the 9,000 subdirectories under `contracts/` contains exactly two files:

| File | Description |
|---|---|
| `contract.sol` | The generated Solidity source code for this contract |
| `quality_evaluation.json` | The standalone five-dimensional quality evaluation for this contract, including per-metric scores, evidence, and the composite score |

All other fields (ABI, security audit report, contract schema, ground-truth code and scores, compilation result, and timing metadata) are available in the corresponding entry in `smarteval_contracts.jsonl`, matched by the zero-padded contract ID (e.g., directory `0001/` corresponds to the first entry in the JSONL).

## Intended Use and Evaluative Claims

This dataset is intended to support the following evaluative uses:

- Benchmarking LLM code generation quality for Solidity smart contracts against a structured five-dimensional rubric
- Studying characteristic failure modes in natural language to code synthesis, including logic omissions, state transition errors, and complexity-driven degradation
- Comparing LLM-generated implementations against expert developer baselines on specification fidelity, variable naming, FSM correctness, and business logic accuracy
- Ablation studies on code generation pipeline components using per-contract provenance metadata
- Training or fine-tuning models for smart contract quality assessment

The dataset supports the claim that LLM-generated contracts score higher on specification fidelity metrics than expert-written ground-truth implementations (+8.29 composite points on average) due to literal specification-following behavior, while expert developers make architectural and gas-efficiency trade-offs not captured by the rubric.

## Limitations

Users should be aware of the following limitations before drawing conclusions from this dataset:

**Compilation does not imply correctness.** A contract that compiles successfully and receives a high rubric score may still behave incorrectly on specific input sequences, violate economic invariants under adversarial conditions, or fail state-transition guards in edge cases. The rubric measures specification fidelity, not runtime correctness or formal verification.

**Gas efficiency is not measured.** The five-dimensional rubric does not include a gas optimization metric. Contracts that score highly may be economically impractical on mainnet where transaction costs are significant.

**Coverage is limited to FSM-SCG contract types.** The dataset covers token standards (ERC20, ERC721), crowdsales, governance, staking, escrow, and access control. Cross-contract interactions, oracle dependencies, upgradeable proxy patterns, and regulatory compliance requirements are not represented.

**Ground-truth Solidity version range.** The FSM-SCG ground-truth contracts span Solidity versions 0.4.x to 0.8.x. Compilation of older ground-truth contracts under the 0.8.x compiler used for generated contracts may fail due to syntax changes rather than semantic errors.

**LLM auditor is not a substitute for formal verification.** The security audit reports are produced by a GPT-4o-mini auditor agent. The 79.4% category agreement rate with Slither confirms the auditor detects real patterns, but 20.6% of flagged categories may not correspond to independently verifiable findings, and the auditor does not detect execution-path bugs or economic exploits that require dynamic analysis.

**Single model generation.** All 9,000 contracts were generated using GPT-4o-mini. Quality and failure mode distributions may differ substantially for other models.

## Data Collection and Generation Process

The generated contracts were produced by a seven-phase multi-agent pipeline. Specifications from the FSM-SCG dataset were first parsed into a structured schema by a requirement extraction agent, then passed to a Solidity generation agent configured as a senior smart contract engineer. Generated contracts underwent security auditing and iterative severity-gated refinement (up to one refinement cycle for the main corpus), followed by ABI generation and five-dimensional quality evaluation. Each generated contract was also evaluated against its paired FSM-SCG ground-truth implementation using the same rubric. All phases used GPT-4o-mini and were run in six parallel batches of 1,500 contracts each.

No personally identifiable information is present in any component of this dataset. The FSM-SCG specifications are synthetic or anonymized contract descriptions; no real-world contract addresses, wallet addresses, or user data appear in the dataset.
